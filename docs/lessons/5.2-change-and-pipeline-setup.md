# 5.2 変更要求・資源更新とCIパイプラインの準備

## 目的

Issue、branch、Draft Pull Request、最小PR CIをつなげ、`pr-ci-gate`を初めて成功させる。その成功後にmain branch用Rulesetを完成させ、品質ゲートによってmainへのmergeを制御できる状態にする。

## 開始状態

5.1の準備が完了し、次の状態になっている。

- 受講者本人の個人GitHubアカウントがOwnerの演習用リポジトリがある。
- GitHub Actionsを利用できる。
- merge方式が設定されている。
- main branch用RulesetはRequired status checkなし、`Disabled`で保存されている。
- `.github/workflows/pr-ci.yml`は`workflow_dispatch`だけを持つスターターで、完成版品質jobはまだない。

## 終了状態

- Issueに対応するbranchとDraft Pull Requestが作成されている。
- `governance-check`、Test run ID生成、governance証跡、Job Summary、`pr-ci-gate`を含む最小PR CIが一度successになっている。
- RulesetのRequired status checkに`pr-ci-gate`だけが登録されている。
- `Require branches to be up to date before merging`が有効である。
- RulesetのEnforcement statusが`Active`で、Bypass listが空である。
- PR CIが失敗、未完了、または古いmainを基準にした結果だけではmainへmergeできない。

## 操作手順

### 1. 変更Issueを作成する

[Issue Form](../../.github/ISSUE_TEMPLATE/change-request.yml)を使い、次を入力する。

1. `background`へ変更の背景と目的を入力する。
2. `change_summary`へ変更内容を入力する。
3. `acceptance_criteria`へ受入条件を入力する。
4. `affected_resources`へ変更対象資源を入力する。
5. `target_version`へ対象バージョンを入力する。
6. `required_final_stage: UT`を確認する。

Issue番号、Test run ID、Environment face ID、Build Artifact IDなどの実行時情報は、受講者がIssue本文へ入力しない。

### 2. branchを作成する

作成されたIssue番号を使い、`feature/issue-<number>-<short-description>`形式のbranchを作成する。

### 3. 5.2の段階資源を適用する

5.2のpatchは、スターターworkflowを最小PR CIへ置き換え、governance判定とそのテストを追加する。cleanなworking treeで、適用可否を確認してから適用する。

```bash
bash scripts/exercises/apply-learning-stage.sh --check 5.2
bash scripts/exercises/apply-learning-stage.sh 5.2
git diff --check
git diff
```

`governance-check`と`pr-ci-gate`だけが追加され、5.3以降の品質jobが含まれていないことを確認する。適用を取り消す場合は、commit前に次を実行する。

```bash
git apply -R exercises/5.2/patches/lesson.patch
```

patchが適用できない場合は、working treeがcleanか、公開スターターから開始しているかを確認する。[トラブルシューティング](../troubleshooting/README.md)でstage順を確認し、必要なファイルだけを[`reference/completed/`](../../reference/completed/)と比較する。

### 4. 5.2の変更をcommitする

Issue番号を含むcommit messageで5.2の変更をcommitする。次のstageを適用する前に、`git status`がcleanであることを確認する。

### 5. Draft Pull Requestを作成する

[Pull Requestテンプレート](../../.github/pull_request_template.md)を使い、本文に次を含める。

```text
Closes #<issue-number>

target_version: <version>
required_final_stage: UT
```

### 6. 最小PR CIを確認する

Pull Requestを作成すると[PR CI workflow](../../.github/workflows/pr-ci.yml)が開始される。Actionsのworkflow runとJob Summaryで次を確認する。

- Pull Request本文とbranch名から同じIssue番号候補が抽出されている。
- Test run IDが`TR-UT-ISSUE-<issue-number>-<workflow-run-id>-A<run-attempt>`形式で生成されている。
- `governance-check`がIssue、branch、Pull Request metadataを検証している。
- `evidence-governance_<test-run-id>`が生成されている。
- Job SummaryにTest run ID、Issue、Pull Request、workflow run/attempt、証跡Artifact名が表示されている。
- `pr-ci-gate`がsuccessになっている。

Issueを一意に関連付けられない場合、Test run IDは`TR-UT-UNLINKED-<workflow-run-id>-A<run-attempt>`となり、`governance-check`と`pr-ci-gate`はfailureになる。適当なIssue番号で補完せず、branch名とPull Request本文を修正する。

### 7. `pr-ci-gate`をRequired status checkへ登録する

初回の`pr-ci-gate` successを確認した後、[リポジトリ設定手順](../setup/repository-settings.md)のPhase Bを実施する。

1. Phase Aで作成した`main-protection` Rulesetを開く。
2. `Require status checks to pass before merging`を有効にする。
3. Required status checkとして`pr-ci-gate`だけを追加する。
4. `Require branches to be up to date before merging`を有効にする。
5. Enforcement statusを`Active`にする。
6. Bypass listが空であることを確認して保存する。

### 8. 品質ゲートとの接続を確認する

Draft Pull Requestのmerge欄で、`pr-ci-gate`とbranch更新条件がmerge条件になっていることを確認する。`pr-ci-gate`がfailure、cancelled、skipped、未完了の場合や、mainの更新後にbranchが古くなった場合はmergeできない。

## 学習上重要なポイント

`pr-ci-gate`は解析やテストを再実行せず、PR CI内の品質関連job結果を集約する。先行jobのfailure、cancelled、skippedによる通常の依存関係上のskipを防ぐため、`if: always()`相当で実行する。

5.2では、実装済みの最小処理だけを`pr-ci-gate`が集約する。後のレクチャーでは、追加した品質関連jobを順番に集約対象へ加える。未実装jobを成功扱いにするstub jobは作成しない。

Required status checkは`pr-ci-gate`の1本だけにする。strict設定により、mainが更新された場合は最新mainを取り込み、新しいhead SHAに対してPR CIを再実行してからmergeする。
