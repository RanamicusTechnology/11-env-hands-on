# 5.4 使い捨てテスト環境の構築・デプロイ・削除

## 目的

Terraform Docker Provider、Ansible infra、Ansible deploy、UT環境上の起動・疎通確認、cleanup、残存確認により、使い捨てUT環境面を構築して削除する流れを理解する。

## 開始状態

5.3の段階資源がcommit済みで、`Temporary`状態のBuild Artifactが生成され、同一Build Artifactを後続jobへ渡せる状態。

## 終了状態

GitHub-hosted runner上でUbuntu 24.04 target containerを含むUT環境面が構築され、NginxとGoアプリが構成・デプロイされ、Build Artifact由来のGoバイナリについて最低限の起動・疎通確認が行われ、cleanupと残存確認が試行される。

## 受講者が操作・確認する内容

- cleanなworking treeで`bash scripts/exercises/apply-learning-stage.sh --check 5.4`を実行する
- `bash scripts/exercises/apply-learning-stage.sh 5.4`で5.4 patchを適用し、`git diff --check`と`git diff`で差分を確認する
- 5.4のCI結果を確認した後、5.5を適用する前に5.4の変更をcommitする
- Test run IDは5.2で生成済みであることを確認する
- Environment face IDが`UT-<issue-number>-<workflow-run-id>-A<run-attempt>`形式で生成されることを確認する
- PR CIへ環境構築、infra構成、deploy、UT環境上の起動・疎通確認、cleanupの呼び出しを接続する
- Build Artifactから展開したGoバイナリの配置、実行権限、process、port listen、direct HTTP、Nginx経由HTTP、version一致を確認する方針を確認する
- Terraform labelsとAnsibleの責務分離を確認する
- cleanup warningの扱いを確認する
- cleanup前にログを退避し、cleanup後にdestroy logと残存確認をenvironment証跡へ追加する方針を確認する
- environment-lifecycle job内で`evidence-environment_<test-run-id>`を最終化してuploadする順序を確認する
- 静的解析やGo単体テストで早期失敗した場合も、environment-lifecycle jobがcleanup対象0件としてcleanupと残存確認を実行し、`cleanup_state: Completed`を記録する方針を確認する
- 環境構築、Ansible、cleanup関連結果をPR CI内の`pr-ci-gate`へ段階的に追加することを確認する

## 段階資源

- `exercises/5.4/patches/lesson.patch`
- PR CIの`environment-lifecycle` job
- Terraform Docker ProviderによるUT環境定義
- Ubuntu 24.04 target image Dockerfile
- Ansible infra/deploy role
- 5.3で生成したBuild Artifactを再buildせずUT環境へ配置する処理
- 起動・疎通確認処理
- cleanupと残存確認処理
- `evidence-environment_<test-run-id>`のmanifest、summary、logs

patchをcommit前に取り消す場合は、`git apply -R exercises/5.4/patches/lesson.patch`を実行する。適用できない場合は、5.3までが順番どおりに適用・commit済みかとworking treeがcleanかを[トラブルシューティング](../troubleshooting/README.md)で確認し、完成状態の個別ファイルは[`reference/completed/`](../../reference/completed/)と比較する。

## 学習上重要なポイント

infra構成とapp deployを混在させない。Test run ID生成は5.2で完了済みであり、5.4ではEnvironment face IDを生成して、Terraform labelsにTest run IDとEnvironment face IDを関連付ける。Environment face IDにはrun attemptを含め、workflow再実行時に以前の試行と衝突しないようにする。

cleanup失敗はwarningとして扱うが、cleanup未実行は品質ゲートfailureである。正常系の受け入れ確認ではcleanup成功と残存なしを確認する。テスト結果・証跡はBuild Artifactの一部ではなく、Test run IDを中心に管理する。

UT環境上の起動・疎通確認は、詳細な受入テストではない。GoバイナリがBuild Artifactから期待パスへ配置されていること、実行権限があること、プロセスが起動していること、期待portがlistenしていること、appへ直接HTTPで到達できること、`/health`がHTTP 200を返すこと、Nginx経由でappへ到達できること、実行中app versionがBuild Artifact versionと一致することを確認し、失敗時もcleanupと残存確認へ進む。

環境が作成されていない早期失敗経路でも、cleanupと残存確認は不要扱いにしない。cleanup対象0件として処理し、残存がなければ`cleanup_state: Completed`とする。cleanup不要を表す別状態は作らない。

## 確認する項目

- Job Summaryで`Environment face ID`、environment creation state、test result、cleanup stateを確認する
- `evidence-environment_<test-run-id>`からTerraform plan/apply/destroy log、Ansible log、起動・疎通確認logを確認する
- cleanup target count、remaining resource count、cleanup warningを確認する
- 早期失敗時に環境未作成、cleanup target 0、`cleanup_state: Completed`として記録されていることを確認する
- 正式なインフラテスト群とAPIテスト群は5.5以降で追加されることを確認する

20分程度を目安とするが、Terraform/Ansibleのログ確認により変動する。
