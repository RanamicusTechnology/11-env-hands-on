# 5.4 使い捨てテスト環境の構築・デプロイ・readiness確認・削除

## 目的

Terraform Docker Provider、Ansible infra、Ansible deploy、UT環境上の起動・疎通確認（readiness check）、cleanup、残存確認により、使い捨てUT環境面を構築して削除する流れを理解する。

5.2で作成した同じ変更Issue、同じfeature branch、同じDraft Pull Requestを引き続き使用する。5.4のreadiness checkは正式テストそのものではない。正式インフラテストと正式APIテストは5.5で扱う。

## 開始状態

- 5.3の変更がcommit、push済みで、working treeがcleanである。
- `build-go-app_<test-run-id>`を生成し、後続jobへ渡せる。
- Draft Pull Requestのmetadataは`target_version: 0.0.0`、`required_final_stage: UT`のままである。

## 終了状態

GitHub-hosted runner上でUbuntu 24.04 target containerを含むUT環境面が作成される。NginxとGoアプリを構成・デプロイし、Build Artifact由来のGoバイナリへ起動・疎通確認（readiness check）を行った後、cleanupと残存確認を試行する。

Test run IDを生成する仕組みは5.2で追加済みである。Test run ID自体はworkflow runごとに新しく生成され、再実行ではrun attemptを含む新しいIDになる。

### 2. 変更をcommitしてpushする

実際の差分に合わせてstage対象を調整する。

```bash

git diff --cached --check
git commit -m "feat: add lesson 5.4 disposable UT environment (#<issue-number>)"

```

`<issue-number>`は5.2から継続しているIssue番号へ置き換える。5.5を適用する前に、Draft Pull RequestのPR CIを確認する。

適用できない場合は、5.3までが順番どおりに適用・commit済みか、working treeがcleanかを[トラブルシューティング](../troubleshooting/README.md)で確認する。

## GitHub画面とArtifactで確認すること

Pull Requestの`Checks`タブ、`environment-lifecycle` Job Summary、`evidence-environment_<test-run-id>`を確認する。

- Environment face IDが`UT-<issue-number>-<workflow-run-id>-A<run-attempt>`形式である。
- environment creation stateとreadiness check結果が記録されている。
- `build-go-app_<test-run-id>`をdownloadし、checksumとversionを検証している。
- Terraform plan/apply log、Ansible log、起動・疎通確認logがある。
- cleanup前に必要なログをrunner上へ退避している。
- cleanup後にTerraform destroy log、cleanup log、残存確認logを追加している。
- cleanup target count、cleanup state、cleanup warning、remaining resource countがある。
- environment evidence manifestを最終化してからArtifactをuploadしている。
- `pr-ci-gate`が環境ライフサイクル結果を集約している。

主なArtifact構成は次のとおり。

```text
evidence-environment_<test-run-id>/
├── manifest.json
├── environment-lifecycle-result.json
├── summary.md
└── logs/
    ├── terraform-plan.log
    ├── terraform-apply.log
    ├── ansible.log
    ├── startup-connectivity-check.log
    ├── terraform-destroy.log
    ├── cleanup.log
    └── residue-verification.log
```

失敗時は、Job Summaryを入口に`environment-lifecycle-result.json`、該当log、cleanup log、residue verification logの順で確認する。

## 仕組みとして理解すること

### Environment face IDとTerraform labels

Environment face IDは、一回のworkflow試行で作成するUT環境面を識別する。run attemptを含むため、再実行時に以前の試行と衝突しない。Terraform labelsはTest run IDとEnvironment face IDをDocker資源へ関連付け、cleanupと残存確認の対象選択に使用する。

### TerraformとAnsibleの責務

Terraformはcontainerやnetworkなど環境面の作成・削除を担当する。Ansible infraはNginxなどインフラ構成、Ansible deployはBuild Artifact由来のGoアプリ配置・起動を担当する。infra構成とapp deployを混在させない。

### 起動・疎通確認（readiness check）

5.4は、Build Artifactを展開してappを起動でき、process、port、HTTPの最低限の前提が成立し、正式テストを開始してよい状態かを手続き的に確認する。Build Artifact由来のGoバイナリの配置、実行権限、process、port listen、direct HTTP、`/health`のHTTP 200、Nginx経由HTTP、実行中version一致を確認し、前提不成立なら正式テスト前にfail-fastする。

このreadiness checkは正式テストケース13件に含めない。process、port、Nginx経由`/health`、versionは5.5でも確認するが、5.4は正式テスト開始の前提確認、5.5は受入・回帰証跡としてのcase単位確認であり、目的が異なる。

### 早期失敗とcleanup target 0

静的解析、Go単体テスト、build/packageなどで早期失敗し、UT環境を作成しない場合も`environment-lifecycle`を通常skipしない。cleanup対象0件としてcleanup手順と残存確認を実行し、残存がなければ`cleanup_state: Completed`とする。cleanup不要を表す別状態は作らない。

cleanupで削除に失敗した場合は`CompletedWithWarning`として警告を記録できるが、cleanupまたは残存確認を実行できない`NotAttempted`は品質ゲートfailureである。

テスト結果・証跡はBuild Artifactへ同梱せず、Test run IDを中心にjobごとのArtifactとして管理する。
