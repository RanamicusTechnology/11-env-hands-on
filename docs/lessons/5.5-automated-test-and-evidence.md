# 5.5 自動テスト・結果証跡管理とCIパイプラインの完成

## 目的

5.4で作成した使い捨てUT環境面に、正式なインフラテストとAPIテストを追加し、テスト結果、ログ、JUnit XML、JSON summary、Markdown summary、environment evidence manifestをPR CIの品質ゲートへ接続する。

このレクチャーでは、Promotion Candidate Record、Release Candidate登録、Draft Release、GHCR pushは扱わない。これらはセクション5の受講者向けPR CIの範囲外である。

## 開始状態

5.4の段階資源がcommit済みで、`environment-lifecycle` jobが次を実行できる状態。

- 5.3で生成した`build-go-app_<test-run-id>`をdownloadする
- Terraform Docker ProviderでUT環境面を作成する
- AnsibleでNginx構成とGoアプリdeployを行う
- 最小限の起動・疎通確認を行う
- cleanup前ログ退避、cleanup、残存確認を行う
- `evidence-environment_<test-run-id>`をuploadする

## 終了状態

`environment-lifecycle`内で、最小起動・疎通確認の後に次を実行する。

- pytest + Testinfraによる正式インフラテスト
- pytest + requestsによる正式APIテスト
- インフラ/APIテストのlog、JUnit XML、JSON summary、Markdown summaryの保存
- environment evidence manifestへの個別テスト結果の記録
- `pr-ci-gate`による正式テスト結果、証跡完全性、cleanup state、残存0件の判定

## 受講者が確認する内容

1. cleanなworking treeで`bash scripts/exercises/apply-learning-stage.sh --check 5.5`を実行する
2. `bash scripts/exercises/apply-learning-stage.sh 5.5`で5.5 patchを適用し、`git diff --check`と`git diff`で差分を確認する
3. `environment-lifecycle`のJob Summaryで、インフラテストとAPIテストの結果を確認する
4. `evidence-environment_<test-run-id>`の`manifest.json`を確認する
5. `test-results/infrastructure-test-junit.xml`と`test-results/api-test-junit.xml`を確認する
6. `test-results/*-result.json`で、実行状態、結果、失敗理由、log pathを確認する
7. `summaries/*-summary.md`で、人間向けのテスト結果を確認する
8. `logs/infrastructure-test.log`と`logs/api-test.log`を確認する
9. cleanupと残存確認が、テスト成功・失敗にかかわらず実行されることを確認する
10. `pr-ci-gate`が正式テスト結果、`missing_evidence_count: 0`、`environment_evidence_complete: true`、`remaining_resource_count: 0`を判定していることを確認する
11. CI成功後に5.5の変更をcommitし、5.6はこのcleanな完成状態から開始する

patchをcommit前に取り消す場合は、`git apply -R exercises/5.5/patches/lesson.patch`を実行する。適用できない場合は、5.4までが順番どおりに適用・commit済みかとworking treeがcleanかを[トラブルシューティング](../troubleshooting/README.md)で確認する。5.5完了状態は[`reference/completed/`](../../reference/completed/)の個別ファイルと比較できる。

## インフラテストとAPIテストの違い

インフラテストは、UT環境面が期待どおりに構成され、Build Artifact由来のGoアプリが配置・起動されていることを確認する。主な対象は、Docker container/networkとlabel、Nginx設定、Goアプリbinary、実行権限、process、port listen、Nginx経由`/health`である。

APIテストは、受講者や利用者が見るHTTP APIの振る舞いを確認する。主な対象は、Nginx reverse proxy経由の`/health`、HTTP status、JSON body、Build Artifact version一致、未対応method、未定義pathである。

## 証跡ファイルの関係

`evidence-environment_<test-run-id>`には、5.4で扱ったTerraform、Ansible、startup、cleanup、残存確認ログに加えて、次を含める。

```text
logs/infrastructure-test.log
logs/api-test.log
test-results/infrastructure-test-junit.xml
test-results/api-test-junit.xml
test-results/infrastructure-test-result.json
test-results/api-test-result.json
summaries/infrastructure-test-summary.md
summaries/api-test-summary.md
```

`manifest.json`の`expected_evidence`、`collected_evidence`、`missing_evidence`、`missing_evidence_count`、`environment_evidence_complete`は、期待した証跡が揃ったかを確認する入口である。placeholderは調査補助であり、証跡欠落を正常化するものではない。欠落をplaceholderで隠さず、skipや`FailedBeforeTest`の理由はJSON summaryとMarkdown summaryへ残す。

## 品質ゲートで判定すること

`pr-ci-gate`は解析やテストを再実行しない。先行jobの結果とoutputsを集約し、次を判定する。

- `governance-check`、`static-analysis`、`unit-test`、`build-package`、`environment-lifecycle`が成功していること
- 必須証跡ArtifactとBuild Artifactのuploadが成功していること
- environment evidence manifestがfinalizeされていること
- `infrastructure_test_result: Passed`
- `api_test_result: Passed`
- `missing_evidence_count: 0`
- `environment_evidence_complete: true`
- `cleanup_state`が`Completed`または`CompletedWithWarning`
- `cleanup_state`が`NotAttempted`ではないこと
- `remaining_resource_count: 0`

cleanup warningは、品質不良ではなく運用上の警告としてJob Summaryと証跡に残す。ただし残存リソースがある場合、またはcleanupを試行できなかった場合は品質ゲート失敗にする。

## 異常時の見方

インフラテストが失敗した場合、APIテストは前提不成立としてskipする。`api_test_result: Skipped`は正常系の合格ではないため、`pr-ci-gate`はfailureになる。

APIテストだけが失敗した場合、インフラテストの結果とAPIテストの結果を分けて確認する。Nginxやprocessは正常でも、HTTP APIの振る舞いが期待と異なる場合がある。

テスト失敗時も、cleanup、残存確認、environment evidence manifest finalization、Artifact uploadを可能な限り実行する。失敗原因の追跡には、テストログ、JUnit XML、JSON summary、cleanup log、residue verification logを合わせて確認する。

## 想定時間

20分程度を目安とする。証跡Artifactの中身を確認する時間を含めると増減する。
