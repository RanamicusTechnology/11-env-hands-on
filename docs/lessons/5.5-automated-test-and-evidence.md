# 5.5 自動テスト・結果証跡管理とCIパイプラインの完成

## 目的

5.4の使い捨てUT環境面へ正式インフラテストと正式APIテストを追加する。テスト結果、ログ、JUnit XML、JSON result、Markdown summary、environment evidence manifestを品質ゲートへ接続し、Ready for review、merge、Issue closeまでを完了する。

5.2で作成した同じ変更Issue、同じfeature branch、同じDraft Pull Requestを引き続き使用する。Promotion Candidate Record、Release Candidate登録、Draft Release、GHCR pushは扱わない。

## 開始状態

- 5.4の変更がcommit、push済みで、working treeがcleanである。
- Draft Pull Requestのmetadataは`target_version: 0.0.0`、`required_final_stage: UT`のままである。
- `environment-lifecycle`がBuild Artifactのdownload、UT環境作成、Ansible構成・deploy、起動・疎通確認（readiness check）、cleanup、残存確認、environment証跡uploadを実行できる。

## 終了状態

`environment-lifecycle`が起動・疎通確認（readiness check）後に、事前定義したインフラ9件とAPI 4件の正式テストを実行する。`pr-ci-gate`が正式テスト結果、証跡完全性、cleanup state、残存0件を判定する。

5.2から継続したDraft Pull RequestをReady for reviewへ変更し、最新headと最新mainに対する品質ゲートを確認してmergeする。`Closes #<issue-number>`により変更Issueがcloseされ、feature branchを削除できる。

## 1. 5.5段階patchを適用する

```bash

```

正式インフラテスト、正式APIテスト、13件のテストケースカタログ、テスト結果生成、証跡完全性判定、品質ゲートの変更が追加されていることを確認する。

## 2. 変更をcommitしてpushする

実際の`git diff --name-only`を確認し、変更したpathだけをstageする。次は標準例である。

```bash
git status
git add .github/workflows/pr-ci.yml scripts/pr-ci tests
git diff --cached --check
git commit -m "feat: complete lesson 5.5 PR CI (#<issue-number>)"
git push
```

`<issue-number>`は5.2から継続しているIssue番号へ置き換える。

> [!CAUTION]
> 5.5 patchをcommit前に取り消す場合だけ、次を実行する。
>
> ```bash
> git apply -R exercises/5.5/patches/lesson.patch
> ```

適用できない場合は、5.4までが順番どおりに適用・commit済みか、working treeがcleanかを[トラブルシューティング](../troubleshooting/README.md)で確認する。

## 3. 正式テストの役割を確認する

正式インフラテストは、`tests/testcases/README.md`で事前定義した`INF-001`～`INF-009`をpytest + Testinfraで実行する。UT環境面が期待どおりに構成され、Build Artifact由来のGoアプリが配置・起動されていることを、Docker container/networkとlabel、Nginx設定、binary、実行権限、process、port listen、Nginx経由`/health`などのcase単位で確認する。

正式APIテストは、同じカタログで事前定義した`API-001`～`API-004`をpytest + requestsで実行する。利用者が見るHTTP APIの振る舞いとして、Nginx reverse proxy経由の`/health`、HTTP status、Content-Type、JSON body、Build Artifact version一致、未対応method、未定義path、container直接応答との一致をcase単位で確認する。

各caseは安定したID、automation function、事前定義した期待結果、主な証跡path、skip条件を持つ。正常なLesson 5.5のPR CIでは13件すべてが実行対象であり、`API-004`だけは`TARGET_CONTAINER_NAME`がない場合に条件付きskipする。

5.4のreadiness checkは、正式テストを開始できる状態かをfail-fastで確認する前提確認であり、正式テスト13件に含めない。process、port、Nginx経由`/health`、versionを5.5で意図的に再確認するのは、受入・回帰証跡としてJUnitへcase単位結果を残すためである。workflow順序とGate条件は変わらない。

## 4. environment証跡を順番に読む

Actionsのworkflow runから`evidence-environment_<test-run-id>`をdownloadし、次の順序で確認する。

1. `manifest.json`
2. `environment-lifecycle-result.json`
3. `test-results/*-test-result.json`
4. `summaries/*-test-summary.md`
5. `test-results/*-test-junit.xml`
6. `logs/*-test.log`
7. `logs/terraform-destroy.log`、`logs/cleanup.log`、`logs/residue-verification.log`
8. `pr-ci-gate` Job Summary

主な構成は次のとおり。

```text
evidence-environment_<test-run-id>/
├── manifest.json
├── environment-lifecycle-result.json
├── summary.md
├── test-results/
│   ├── infrastructure-test-result.json
│   ├── api-test-result.json
│   ├── infrastructure-test-junit.xml
│   └── api-test-junit.xml
├── summaries/
│   ├── infrastructure-test-summary.md
│   └── api-test-summary.md
└── logs/
    ├── infrastructure-test.log
    ├── api-test.log
    ├── terraform-destroy.log
    ├── cleanup.log
    └── residue-verification.log
```

`manifest.json`は期待した証跡、収集した証跡、欠落した証跡と全体状態の入口である。result JSONで実行状態・結果・失敗理由・log pathを確認し、Markdown summaryとJUnit XML、実ログを順に突き合わせる。

Build Artifactとjobごとの証跡Artifactは、いずれもActions Artifactへのupload時点から30日保持する。workflow runの保持期間、Git履歴、外部保管先の保持期間とは別の設定である。

実行前failureや先行テストfailureによるskipでは、調査情報を残すためplaceholderを作る場合がある。placeholderは実行状態とskip理由を追跡する補助であり、必要な証跡の欠落を合格扱いにするものではない。欠落があれば`missing_evidence`へ残し、`missing_evidence_count > 0`または`environment_evidence_complete: false`なら`pr-ci-gate`はfailureになる。

## 5. 品質ゲートを確認する

`pr-ci-gate`は解析やテストを再実行しない。先行jobの結果とoutputsを集約し、少なくとも次を判定する。

- `governance-check`、`static-analysis`、`unit-test`、`build-package`、`environment-lifecycle`がsuccessである。
- 必須証跡ArtifactとBuild Artifactのuploadがsuccessである。
- environment evidence manifestがfinalizeされている。
- `infrastructure_test_result: Passed`。
- `api_test_result: Passed`。
- `missing_evidence_count: 0`。
- `environment_evidence_complete: true`。
- `cleanup_state`が`Completed`または`CompletedWithWarning`で、`NotAttempted`ではない。
- `remaining_resource_count: 0`。

cleanup warningは、使い捨て環境の削除または残存確認で警告があったことを示す。品質処理と正式テストがPassedで、cleanupを試行し、残存0件なら運用上の警告として記録できる。残存がある場合やcleanupを試行できない場合は品質ゲートfailureである。

## 6. Ready for reviewからmerge、Issue closeまで進める

次の順序で5.2から続けた変更を完了する。

1. 5.5のcommitが同じfeature branchへpush済みであることを確認する。
2. GitHubのPull Request画面で`Ready for review`を選択する。
3. `ready_for_review`イベントで起動した最新PR CIを開く。
4. 最新head SHAに対する`pr-ci-gate`がsuccessであることを`Checks`タブで確認する。
5. feature branchが最新mainを取り込んでいることを確認する。更新が必要ならGitHubの`Update branch`、またはローカルでmainをmergeしてpushし、新しいheadのPR CIを待つ。
6. Pull Requestの`Conversation`画面下部で、`pr-ci-gate`とbranch更新を含むRulesetのmerge条件をすべて満たしていることを確認する。
7. 許可されたmerge方法を選び、Pull Requestをmergeする。
8. Pull Request本文の`Closes #<issue-number>`により、5.2で作成した変更Issueがcloseされたことを確認する。
9. GitHubの`Delete branch`を選択し、feature branchが削除されたことを確認する。

Ready for review後にmainが更新された場合は、branchを更新して新しいhead SHAの`pr-ci-gate` successを確認し直す。古いheadのsuccessだけでmergeしない。

## 異常時の見方

インフラテストがfailureの場合、APIテストは前提不成立として`Skipped`になる。`Skipped`は正常系の合格ではないため、`pr-ci-gate`はfailureになる。

APIテストだけがfailureの場合は、インフラテストがPassedであることを先に確認し、HTTP APIの振る舞いを調べる。

テストfailure時もcleanup、残存確認、manifest finalization、Artifact uploadを可能な限り実行する。調査ではmanifest、result、summary、JUnit XML、test log、cleanup／residue logを合わせて読む。
