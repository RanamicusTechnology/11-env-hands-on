# 5.6 品質ゲートと異常系のハンドリング

## 目的

Goアプリ、IaC、テスト結果・証跡へ演習用patchで意図的な不備を注入し、次を確認する。

- scenarioが期待する層でfailureになる。
- `pr-ci-gate`が不備のある変更のmainへのmergeを止める。
- Job Summaryと証跡から原因を追跡できる。
- patchのrevertまたは不備の修正後にPR CIがsuccessへ戻る。

品質ゲートはPull Request作成を止めるものではない。不備のある変更をmainへmergeしないための判断を行う。

cleanup warningは、使い捨て環境の削除または残存確認で問題が起きた場合の運用上の警告である。cleanupを試行できない状態や残存リソースがある状態を正常化するものではない。

## 開始状態

- 5.5の正常系Pull Requestをmergeし、変更Issueをcloseしている。
- 正常なmainで`pr-ci-gate`がsuccessになる。
- working treeがcleanである。
- scenarioごとに正常なmainから新しいIssue、branch、Pull Requestを作成する。

5.2から5.5のIssue、branch、Pull Requestは使い回さない。5.6はscenarioごとに独立して実施し、次のscenarioも正常なmainから始める。

## 扱うscenario

必須scenarioは次の5件である。

| id | 期待する失敗job／step | 主な確認先 |
| --- | --- | --- |
| `static-analysis-failure` | `static-analysis` / `app-lint` | gofmt log、静的解析result、environment早期cleanup |
| `unit-test-failure` | `unit-test` / `go-unit-test` | Go test log、JUnit XML、単体テストresult |
| `infrastructure-test-failure` | `environment-lifecycle` / `infrastructure-test` | Testinfra log、JUnit XML、API test skip、cleanup |
| `api-test-failure` | `environment-lifecycle` / `api-test` | API test log、JUnit XML、HTTP API不整合 |
| `test-result-evidence-missing` | `pr-ci-gate` / `evidence-completeness` | manifest、欠落証跡数、証跡完全性 |

`cleanup warning`とresidue verification failureは発展scenarioであり、このレクチャーの必須5件には含めない。

## 1. `scenarios.yml`を読む

[scenario定義](../../exercises/5.6/scenarios.yml)で、選ぶscenarioの次のkeyを確認する。

- `id`: コマンドで指定するscenario ID。
- `purpose`: 何を学ぶための不備か。
- `patch`: 適用するpatch path。
- `expected_failure_job`: failureを確認するjob。
- `expected_failure_step`: job内でfailureを確認するstep。
- `evidence_to_check`: 原因と結果を追跡する証跡。
- `expected_gate_result`: `pr-ci-gate`の期待結果。

期待jobだけでなく期待stepも確認し、別の前提不備が先にfailureになっていないことを確認する。

## 2. scenario専用Issueを作成する

GitHub Web UIでscenarioごとに新しいIssueを作成する。次は共通記入例である。`<...>`をscenario定義と実際のpathへ置き換える。

```text
Title:
[Exercise]: <scenario title>

変更の目的:
<purpose>

変更内容:
<patch>で意図的な不備を注入する。

変更対象:
<patchの変更path>

想定するテスト段階と受入条件:
- <expected_failure_job>がfailureになる
- pr-ci-gateがfailureになる
- <evidence_to_check>を確認できる
- 不備の修正後にpr-ci-gateがsuccessになる

target_version:
0.0.1

required_final_stage:
UT

補足・制約:
演習用Pull Requestはmainへmergeしない。
```

例えば`api-test-failure`では、目的に「正式インフラテストがPassedの状態でAPI仕様不整合を検出する」、変更対象に`VERSION`、`app/health.go`、Nginx template path、受入条件に`environment-lifecycle` / `api-test`とAPI test証跡を記載する。

## 3. 正常なmainからscenario branchを作成する

Issue番号とscenario IDをbranch名へ含める。

```bash
git switch main
git pull --ff-only
git status
git switch -c feature/issue-<issue-number>-api-test-failure
```

別のscenarioでは末尾を`static-analysis-failure`など選択したIDへ置き換える。以前のscenario branchから次のbranchを作成しない。

## 4. scenarioのdry-runを行う

scenario一覧を確認し、標準の事前確認option`--dry-run`を使用する。

```bash
bash scripts/exercises/apply-failure-scenario.sh --list
bash scripts/exercises/apply-failure-scenario.sh --dry-run <scenario-id>
```

`--check`は`--dry-run`の互換aliasであり、既存手順との互換性が必要な場合に使用できる。

```bash
bash scripts/exercises/apply-failure-scenario.sh --check <scenario-id>
```

dry-runはファイルを変更しない。patch path、scenario ID、次の操作を確認する。

## 5. patchを適用してcommit、pushする

```bash
bash scripts/exercises/apply-failure-scenario.sh <scenario-id>
git diff --check
git diff
git add -A
git diff --cached --check
git commit -m "test: exercise <scenario-id> (#<issue-number>)"
git push -u origin HEAD
```

`git diff`では、ルート`VERSION`が`0.0.1`へ更新され、scenario定義が意図する不備とpathだけが変更されていることを確認する。

## 6. scenario Pull Requestを作成する

[Pull Requestテンプレート](../../.github/pull_request_template.md)を使用し、少なくとも次を記載する。

```markdown
## Linked Issue

Closes #<issue-number>

## Change Metadata

target_version: 0.0.1
required_final_stage: UT

## Summary

- Apply <scenario-id>
- Inject one intentional defect for the failure exercise

## Verification

- [ ] <expected_failure_job> fails at <expected_failure_step>
- [ ] pr-ci-gate fails
- [ ] Expected evidence is available
- [ ] pr-ci-gate succeeds after the repair

## Notes

This exercise Pull Request will be closed without merging.
```

このPull Requestは失敗確認と復旧確認のために使用し、successへ戻った後もmainへmergeしない。

## 7. failureと証跡を確認する

次の順序で原因を追跡する。

```text
Pull RequestのChecks
→ expected_failure_job
→ expected_failure_stepとJob Summary
→ evidence Artifact
→ manifest／result／JUnit XML／log
→ pr-ci-gate Summary
```

### `static-analysis-failure`

`evidence-static-analysis_<test-run-id>`の`summary.md`、`static-analysis-result.json`、`logs/gofmt.log`を確認する。`build-package`はskippedになり、`environment-lifecycle`はcleanup target 0と`cleanup_state: Completed`を記録する。

### `unit-test-failure`

`evidence-unit-test_<test-run-id>`の`junit/go-unit.xml`、`logs/go-test.log`、`unit-test-result.json`を確認する。Go単体テストfailureのためBuild Artifactは生成されない。

### `infrastructure-test-failure`

`evidence-environment_<test-run-id>`の`logs/infrastructure-test.log`、infrastructure JUnit XML／result／summary、`manifest.json`を確認する。インフラテストfailure後のAPIテストは`Skipped`となり、cleanupと残存確認は可能な限り実行される。

### `api-test-failure`

正式インフラテストが`Passed`であることを先に確認する。続いてAPI test log、JUnit XML、result、summary、`manifest.json`から未定義pathの不整合を追跡する。

### `test-result-evidence-missing`

正式テスト結果そのものではなく証跡完全性を確認する。`manifest.json`と`environment-lifecycle-result.json`で`missing_evidence`、`missing_evidence_count`、`environment_evidence_complete`を確認する。正式テストがPassedでも、必須証跡が欠落すれば`pr-ci-gate`はfailureになる。

## 8. VERSIONを維持して不備だけを修正する

復旧時もIssueとPull Requestの`target_version`、ルート`VERSION`はすべて`0.0.1`のまま維持する。scenario patch全体を戻すと`VERSION`まで`0.0.0`へ戻り、変更ガバナンスの契約に違反するため、標準の復旧手順には使用しない。

scenario定義の`recovery_method`を確認し、注入した不備だけを次のように修正する。

- `static-analysis-failure`: `gofmt -w app/health.go`を実行する。
- `unit-test-failure`: `app/health_test.go`のService期待値2か所を`ms1-go-api`へ戻し、`go test ./...`を実行する。
- `infrastructure-test-failure`: `ansible/infra/roles/nginx/tasks/main.yml`のNginx site enableだけを`state: link`へ戻す。
- `api-test-failure`: `app/health.go`へ追加された誤った`/not-found` routeと、Nginx templateへ追加された`/not-found` locationだけを削除する。
- `test-result-evidence-missing`: `scripts/pr-ci/environment_lifecycle.py`へ追加された、API test summaryを削除して欠落を記録するscenario専用処理だけを除去する。

修正後は`VERSION`が`0.0.1`であり、差分にscenarioで注入した不備が残っていないことを確認する。

```bash
cat VERSION
test "$(cat VERSION)" = "0.0.1"
git diff --check
git diff
```

修正をcommit、pushする。

```bash
git status
git add <修正した不備のファイル>
git diff --cached --check
git commit -m "fix: recover <scenario-id> exercise (#<issue-number>)"
git push
```

最新headのPR CIを待ち、以前failureだったjobと`pr-ci-gate`がsuccessへ戻ったことを確認する。

## 9. mergeせず演習を終了する

次の順序でscenarioを終了する。

```text
failure確認
→ 注入した不備だけを修正しVERSION 0.0.1を維持
→ 最新headのPR CIとpr-ci-gate successを確認
→ Pull Requestをmergeせずclose
→ Issueへ完了コメントを記録
→ Issueを手動close
→ remoteとlocalのscenario branchを削除
```

Issueコメント例:

```text
異常系演習を完了しました。
期待したjob／stepのfailureと証跡を確認し、修正後のpr-ci-gate successを確認しました。
このPull Requestは教材方針によりmainへmergeせずcloseしました。
```

Pull RequestとIssueをcloseし、必要な差分が残っていないことを確認してからbranchを削除する。演習用branchはmainへmergeしていないため、ローカル削除では`-D`が必要になる。

```bash
git switch main
git pull --ff-only
git push origin --delete feature/issue-<issue-number>-<scenario-id>
git branch -D feature/issue-<issue-number>-<scenario-id>
```

`-D`は未merge branchを破棄するため、Pull Requestのclose、必要な調査記録、修正後successを確認してから実行する。

## 想定時間

1 scenarioあたり20分程度を目安とする。5件すべてを実PRで確認する場合は、GitHub Actionsの待ち時間を含めて複数回に分ける。
