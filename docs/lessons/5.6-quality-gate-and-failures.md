# 5.6 品質ゲートと異常系のハンドリング

## 目的

5.6では、正常なPR CIの本線を壊さず、演習用patchで意図的な不備を注入し、`pr-ci-gate`がmainへのmergeを止めることを確認する。受講者は、失敗したjob、Job Summary、ログ、JUnit XML、JSON result、Markdown summary、evidence manifestを読み、原因を特定して、patchの差し戻しまたは修正によりPR CIをsuccessへ戻す。

品質ゲートの目的は、Pull Requestの作成を止めることではない。不備がある変更をmainへmergeしないよう、PR CIの結果と証跡を集約して判断することである。

期待したjobまたはstepで失敗しない場合は、[トラブルシューティング](../troubleshooting/README.md)でstage完了状態、patch差分、証跡の確認順を確認する。

## 開始状態

- 5.5で、`governance-check`、`static-analysis`、`unit-test`、`build-package`、`environment-lifecycle`、`pr-ci-gate`が実装済みである。
- 5.5の段階資源がcommit済みで、working treeがcleanである。完成状態に疑問がある場合は`reference/completed/`の個別ファイルと比較する。
- `environment-lifecycle`内で正式インフラテストと正式APIテストを実行する。
- environment evidenceにはmanifest、log、JUnit XML、JSON result、Markdown summary、cleanup、残存確認結果が含まれる。
- 正常なmain相当の通常状態では、演習用patchを適用しない限りPR CIがsuccessになる。

## 終了状態

受講者は、scenarioごとに演習用Issue、演習用branch、演習用Pull Requestを作成し、patch適用後に期待どおりPR CIまたは`pr-ci-gate`がfailureになることを確認する。原因確認後はpatchを戻す、または不備を修正し、PR CIがsuccessへ戻ることを確認する。演習用Pull Requestはmainへmergeせずcloseする。

## 扱うscenario

5.6の必須scenarioは次の5件である。

| id | contract scenario | 主な失敗箇所 | patch |
| --- | --- | --- | --- |
| `static-analysis-failure` | `app_lint_failure` | `static-analysis` / `app-lint` | `static-analysis-failure.patch` |
| `unit-test-failure` | `go_unit_failure` | `unit-test` / `go-unit-test` | `unit-test-failure.patch` |
| `infrastructure-test-failure` | `infra_test_failure` | `environment-lifecycle` / `infrastructure-test` | `infrastructure-test-failure.patch` |
| `api-test-failure` | `api_test_failure` | `environment-lifecycle` / `api-test` | `api-test-failure.patch` |
| `test-result-evidence-missing` | `test_result_evidence_missing` | `pr-ci-gate` / evidence completeness | `test-result-evidence-missing.patch` |

`cleanup warning`と`residue verification failure`は発展シナリオとして扱い、このレクチャーの必須scenarioには含めない。

## 演習の進め方

5.2から5.5で使う`apply-learning-stage.sh`は通常状態を段階的に構築するhelperである。5.6では、完成状態へ不備を1件だけ注入する`apply-failure-scenario.sh`を使用し、両者を混同しない。

1. scenarioを1つ選ぶ。
2. scenario専用の変更Issueを作成する。
3. 正常なmain相当のbranchから演習用branchを作成する。
4. `exercises/5.6/scenarios.yml`で目的、patch、期待失敗job、確認する証跡を読む。
5. `bash scripts/exercises/apply-failure-scenario.sh --list`でscenario IDを確認する。
6. `bash scripts/exercises/apply-failure-scenario.sh --dry-run <scenario-id>`または`--check`でpatch適用可否を確認する。
7. `bash scripts/exercises/apply-failure-scenario.sh <scenario-id>`でpatchを適用する。
8. 差分に `VERSION` の更新と、意図した不備が含まれることを確認する。
9. 演習用Pull Requestを作成する。
10. PR CIの失敗job、Job Summary、Actions Artifactを確認する。
11. patchを戻すか、不備を修正する。
12. PR CIがsuccessに戻ることを確認する。
13. 演習用Pull Requestはmainへmergeせずcloseし、対応Issueへ演習完了コメントを残して手動closeする。

通常状態の`VERSION`は`0.0.0`である。各patchは演習用Pull Requestのために`VERSION`を`0.0.1`へ更新する。演習用Pull Request本文には次を含める。

```text
Closes #<scenario用Issue番号>

target_version: 0.0.1
required_final_stage: UT
```

教材資源を仕上げる通常PRでは、演習用patchを適用せず、`target_version: 0.0.0` を使用して教材資源自体を正常状態に保つ。

## scenario別の確認観点

### static-analysis-failure

Goコードへ`gofmt`違反を注入する。確認先は、`static-analysis` job、`summary.md`、`static-analysis-result.json`、`logs/gofmt.log`、`evidence-static-analysis_<test-run-id>`、`pr-ci-gate` Summaryである。`build-package`はskippedになり、`environment-lifecycle`はcleanup target 0と残存確認を記録する。

復旧は、patchを戻すか `gofmt` を実行して差分を修正する。

### unit-test-failure

Go単体テストの期待値を不整合にし、runner上のGoアプリ単体テストを失敗させる。確認先は、`unit-test` job、`junit/go-unit.xml`、`logs/go-test.log`、`unit-test-result.json`、`evidence-unit-test_<test-run-id>`、`pr-ci-gate` Summaryである。

復旧は、patchを戻すか、テスト期待値または実装を整合させる。

### infrastructure-test-failure

Nginx設定の有効化方法を、起動・疎通確認は通るがTestinfraの期待条件に反する状態へ変える。確認先は、`environment-lifecycle` job、`logs/infrastructure-test.log`、`test-results/infrastructure-test-junit.xml`、`test-results/infrastructure-test-result.json`、`summaries/infrastructure-test-summary.md`、`manifest.json`である。

インフラテストが失敗した場合、APIテストは前提不成立としてskipされる。cleanupと残存確認は可能な限り実行される。

### api-test-failure

Go APIに `/not-found` を誤って登録し、正式インフラテストは通したまま、APIテストの未定義path確認を失敗させる。確認先は、`logs/api-test.log`、`test-results/api-test-junit.xml`、`test-results/api-test-result.json`、`summaries/api-test-summary.md`、`manifest.json`である。

復旧は、誤ったrouteを削除するか、期待するHTTP API仕様へ実装を戻す。

### test-result-evidence-missing

正式APIテストのsummaryを生成後に削除し、テスト結果そのものではなく証跡完全性を失敗させる。確認先は、`manifest.json`、`environment-lifecycle-result.json`、`missing_evidence`、`missing_evidence_count`、`environment_evidence_complete`、`pr-ci-gate` Summaryである。

このscenarioでは、正式テストが合格しても `missing_evidence_count > 0` または `environment_evidence_complete: false` であれば品質ゲートはfailureになる。欠落をplaceholderで隠してはならない。

## 証跡の読み取り順序

1. Pull RequestのChecksで、失敗したjobと`pr-ci-gate`を確認する。
2. 失敗jobのJob Summaryで、result、failure reasons、Test run ID、Artifact名を見る。
3. Actions Artifactから該当する`evidence-*_<test-run-id>`をdownloadする。
4. `manifest.json`で`expected_evidence`、`collected_evidence`、`missing_evidence`を見る。
5. `logs/*.log`で実行コマンドと失敗理由を見る。
6. JUnit XMLで失敗test caseを見る。
7. JSON resultとMarkdown summaryで、machine-readableな結果と受講者向け要約を突き合わせる。
8. `pr-ci-gate` Summaryで、どの条件がmerge不可の理由になったか確認する。

## patchの戻し方

patch適用直後であれば、次のように戻せる。

```bash
git apply --unidiff-zero -R exercises/5.6/patches/<scenario>.patch
```

変更を自分で修正する場合は、`VERSION`、PR本文の`target_version`、失敗させた資源を整合させる。修正後はPR CIを再実行し、`pr-ci-gate`がsuccessになったことを確認する。

## mergeしない運用

演習用Pull Requestは、品質ゲートの失敗確認と復旧確認を目的とする。修正後に`pr-ci-gate`がsuccessになってもmainへmergeせず、Pull Requestをcloseする。対応Issueには次の趣旨のコメントを残し、手動でcloseする。

```text
異常系演習を完了しました。
品質ゲートの失敗と修正後の成功を確認しました。
このPull Requestは教材方針によりmainへmergeせずcloseしています。
```

## 想定時間

1 scenarioあたり20分程度を目安とする。5件すべてを実PRで確認する場合は、GitHub Actionsの待ち時間を含めて複数回に分ける。
